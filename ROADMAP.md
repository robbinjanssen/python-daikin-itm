# Roadmap

Where the library is heading: what is still to be added, what should be
improved, and what is left out on purpose, with the reason.
[FEATURES.md](FEATURES.md) has the status per screen of the iTM's web UI; this
file explains the plan behind it.

The library was developed against one iTM. Anything that iTM doesn't have
(equipment, licences, dealer options) can only be built from the web UI's own
code and tested against the simulated iTM in `tests/`. Contributions from people
with other installations are the way to close those gaps; see
[How you can help](#how-you-can-help).

## Still to add

Nothing: every screen of the web UI that isn't left out on purpose (see below)
has a reader, and writes where the screen has settings. What is left is
validating on real iTMs (see "To improve").

| **Validate the functions tested only against the simulated iTM** (marked F in [FEATURES.md](FEATURES.md); their writes need `allow_experimental=True` until then) | Twice a real iTM behaved differently from what the web UI's code suggested: the order of a dialog, and a download's name and duration. Each live test so far either confirmed a function or found a fix. Open, with what each needs: the logged-in user's own language and time and decimal formats (reading, the icon colour, the password and the date format are validated), setting a normal user's allowed screens (graphical screens set up), backup (it starts a job at once), the energy navigator's planned and actual consumption and calendar copy (best with the licence), emergency stop management (the "emergency stop" dealer option) and release (an active stop), the unit settings dialog's optional settings (equipment with hot water, outputs, low noise or a capacity limit), the °F and decimal comma formats, PPD day settings, the filter and dust alarm resets; the dealer-option functions' writes and demand control (the dealer options switched on); the leakage check (outdoor units registered for it, and a 3-hour window); R32 output ports, layout setup and the energy navigator's installer settings (service changes; saving the installer settings restarts the iTM); the password setting; zone member order with Jump. |
| **Validate the fault handling** | Built and tested against the simulated iTM only: a hung iTM costs about one `request_timeout` (the call's clean-up is skipped after a request that got no answer, the logout tried once with `logout_timeout`), a change whose reply was lost raises `WriteOutcomeUnknown` and the next write to the unit first waits for it, the INIT is sent once more after a broken connection, and a progress dialog is waited out by time (`progress_timeout`, 30 s). Still to see on a real iTM: the slowest requests (with `--trace`), before `request_timeout`'s default (30 s) is lowered; the reply to CANCEL_PROG, which the history's load sends after its time (the simulator's reply is a guess); how long a full history takes to load; what the iTM does after its own restart. A read that checks a sent change and gets no answer no longer fails the write: the next read tries again (in a new login when that one ended) until `confirm_timeout`, which also bounds what a hung iTM costs a write's check; a read under way isn't cut at that deadline, as cutting it would end a kept login. |
| **Writes that change nothing: validate the check** | A write never sends a value the unit shows already (decided "better safe": what the iTM forwards to a unit for an unchanged value, and whether the unit stores it, can't be seen, and Daikin limits the control commands to one indoor unit to 7,000 a year in the specification of its DIII-NET Modbus adaptor, without saying why). What it left out (all of it, part of it, or a zone's units that show it; a zone whose units lack different things is written unit by unit) is read for `verify_timeout` (10 s, the 8 s a change was seen to take plus a read) before the call returns, with or without `confirm`, and written after all, once, and confirmed when another change on its way moves it (`NotConfirmed` when it still loses; never a third write). The cost: such a call takes up to 10 s. Tested against the simulated iTM only. Seen on a real iTM before it was built: a remote lock changed by one account and asked back to its old value by another account a moment later was skipped and the first change won. Still to see there: that race ending with the second write's value (with and without confirm, and for a part left out), whether 10 s covers the slowest change, and a zone's unit written through its own panel inside the zone. |
| **History export codes** | The parser names the event, source and value codes seen so far (power, setpoint, fan speed, logins; schedule, overtime timer, temperature limit). Other codes, such as the auto changeover's, are kept as numbers until an export shows them next to the history screen. |
| **Validate the shared session further** | `shared_session()` lets the reads inside its block use one login, so a poll that needs several reads is one login and logout in the iTM's history. Observed on one real iTM (Dutch display language) with `itm check shared-session`, read only: every read in the check (units, points, thermostat status, config, capabilities, the history, the units' settings, the schedule list and every schedule program, among others) gave the same result alone and twice inside a block, and every block kept one login. That covers the icon view's Top button from inside a zone, the POLLING event at the start position, and a menu screen opened again in the same session. A login is cheap there, so the gain is fewer history entries, not time. The energy navigator's further screens (`fetch_energy_navigator[more]` in the check: energy types and groups, equipment details, the rule editor and the rule settings) also gave the same result alone and in a block, with one login per block, on an iTM without the licence; the installer's settings need the service login, which ends the session, so they stay out of the check. A read after another account changed a unit meanwhile (its fan speed) showed the change inside the block, the same as a fresh read, with one login. Still to check: functions that were switched off on that iTM (demand control, energy saving), whose reads came back the same but nearly empty; whether a screen that fills its tabs only when selected opens on its first tab again (`fetch_demand_control`'s graphs go back to it before closing; the energy navigator's budget overview came back complete, but sends every tab at once); and the reads the client still ends the session after (the history of a given day, the units' list view; the analog list view keeps it, see below). A day overview moved ahead (`days_ahead`) and a history paged back (`pages`) now press the screen's Previous or Newer button to get back to the first day or page, and the session stays when that works; `itm check shared-session` runs both (`fetch_schedule_day` per program, one day ahead; `fetch_history[pages]`, two pages), and on the real iTM each gave the same result alone and in a block, with one login per block. Only one step back has been seen there, not longer runs. A sliding temperature read that once took longer in the block did not do so again in repeated runs: inside a block it is faster than alone, as it sends fewer requests; a single slow reply now and then comes from the iTM. `itm status --thermostat` now reads units, thermostat status and capabilities in one login, also on a real iTM (icon view; with `--view list` the capabilities, when they are read, take a second login). `fetch_points(thermostat=...)` reads the thermostat status in the units' own walk (two requests per unit instead of three), and `itm status --thermostat` uses it with the icon view; `itm check shared-session` runs it as `fetch_points[thermostat]`; on the real iTM it gave the same result alone and in a block, with one login. `itm history --unit` and `itm email` read their two screens in one login too (simulated iTM only so far; the history is read last, as the history of a given day ends the session). `itm check reads` shows what a non-administrator account may read; it has run on one real iTM as a temporary normal web user (see "What a normal web user may do" below). |
| **What a normal web user may do** | Done on one real iTM, read only, with `itm check reads` as a temporary normal web user managing one zone and with no allowed screens: the units, points, capabilities, unit settings, thermostat status, zones, layout, indicators, energy saving and own settings read; every read through the main menu failed, as the menu list didn't open (no screen, no dialog). The client now raises `MenuNotAvailable` there, and the README lists what such a user can read and advises an administrator account. Built: `fetch_indicators()` reports it as `menu_available`, and a menu read or write then raises `MenuNotAvailable` without pressing the button (simulated iTM; the empty reply stays the fallback). |
| **Fewer logins for polling clients** | The iTM allows one session per user, so every call logs in and out, and each login and logout is a history entry. `shared_session()` brings the reads of one poll down to one login (see above). **Built: a write in one login** (`confirm_in_session`, on by default): a write and the reads that check it until the change shows use one login, instead of a login per read (three to five for a unit write) or two for a menu write; a pick no other point sends over, a date, the clock or a password typed in a dialog or the service login still ends the write's login, so such a write takes two. A name, a number or a time of day typed in a dialog (CHARINPUT, NUMBER, HOURMIN: names, limits, event times) is saved with its screen's OK and no longer ends the login, so such a write takes one, read back from what the iTM sends again; seen on that iTM for a name (a special day renamed and back) and an event time (a throwaway program's event moved), 3 rounds, one login each, the read-back matching another account's fresh read, and for a number: a setpoint limit switched off and back on (12 writes) took one login each, read back correctly. A menu write's read-back in the same login was checked on that iTM too: a throwaway program's period switched on and off (unticking its checkbox), enabled and disabled, and a special day renamed, 3 rounds, 18 writes; each write's own read-back matched another account's fresh read, with one login per write (two for a rename, whose typed name ends the login). `confirm_in_session=False` gives the old way. **Built, experimental: `kept_session()`** keeps one login for a polling client's lifetime: a POLLING when no request was sent for `keep_alive` seconds (60 by default), a new login on the next call after the iTM ended the session (callers see one extra login), the same token tried again by a POLLING after one that got no answer, a fresh login after `max_age` (3 hours by default), and writes inside only with `allow_experimental`, read back in the same session from what the iTM sends again (a dialog opened anew, a panel value only once the iTM sent it again while other points were shown; otherwise one extra login), never from the client's own pick. The block belongs to the client, so calls from any task use it. Tested against the simulated iTM only (idle expiry by time, changes by another client, a unit that ignores a write). What it builds on was seen on one real iTM with a temporary administrator account: a session left idle still answered after 1, 2, 3 and 4 minutes and had ended after 5 (`SessionEnded`); a session polled every 30 s kept answering for an hour, and its unit reads matched a fresh read by another account every 15 minutes; two accounts were logged in at the same time throughout; a change made meanwhile by another account showed up in a held session's next unit read. A network drop of 60-75 s (connections refused, or requests hanging until the 30 s timeout) didn't end a held session: the same token answered at once afterwards and its reads matched a fresh read by another account. A 2-hour soak on that iTM (a temporary administrator, a read every minute): every comparison with another account's fresh read matched, and a fan speed write read back in the kept session matched a fresh read, with no extra login; but after reads, the iTM ended the session within 3 minutes of idling (a keep-alive at 180 s came too late, while an idle session right after login had answered after 4), so the keep-alive default is 60 s now; with it, 20 minutes without reads kept the same login (a second, 30-minute soak). A read-back test on that iTM (firmware Ver1.32.00, a kept session and a second account reading fresh): in three rounds, power, mode, fan speed and the setpoint lock written and read back in the kept session matched the other account's fresh read every time, with no extra login; a fan speed written through a zone holding only that unit matched too; when the other account overruled a write within seconds, the kept session showed the other account's value, never its own pick; a setpoint change matched in three rounds, on the unit and through a zone, both sides seeing it at the same moment; a setpoint outside the unit's limit was refused by the library before anything was sent. Two menu writes (a schedule event, a special day's name) read back correctly, after one new login, as they type a value. This is what `confirm_in_session` builds on. A write checked in its own login outside a kept session was seen too (the limit writes above, made by another client with the default `confirm_in_session`). Still to validate on a real iTM: how often a write's pick is sent over by another point (in the rounds above it always was), and what the iTM takes the client to show after a pick (the pick or the value before it; the client relies on neither, a write the unit doesn't take has not been seen); what happens after a restart of the iTM; then days of use before the experimental mark goes. | **Language coverage of the newer screens** | The dealer-option, demand, service and energy navigator screens were built from the Dutch labels and the web UI's code; where they read text (activation, options), other display languages are not verified yet. |
| **Compute schedule days: what is still open** | `events_on()` computes a program's events on a date from its weekly pattern, special days, calendar rules and period. Compared on one real iTM (Dutch display language) with `itm schedule NAME --on DATE --compare` and the day overview, using a throwaway program: the calendar row format, the ranking of overlapping rules (a date rule beats an nth-weekday rule; of the same kind, the rule lowest in the calendar list wins, whether it is for one month or every month), "4th" and "Last" on the same date, and a special day replacing the weekday also when it is empty all match. The day overview shows disabled programs, ignores the period, and reaches 7 days ahead but not 14. On a day without events the iTM sends an empty list that still names its columns; the library decodes it, and stepping the day overview onto such a day and past it works on a real iTM. A renamed special day shows its new name in the calendar rows, the pattern option list and the pattern labels, and the computed events still match. "1st".."4th" is the nth occurrence of the weekday in the month (days 1-7, 8-14, ...), not a row of the month's calendar: seen on a first Sunday that was in the calendar's second row. An enabled program ran its weekday event on a date inside its period and not on one outside it; the history shows each run as a schedule row, also for an event that changes nothing. A period's first and last day both count, a period whose end comes before its begin runs over the new year, and a calendar rule naming a date outside the period doesn't run either. Two special days can't share a name: the iTM refuses renaming one to another's name or key ("the name exists already"), so a calendar row's name always points to one special day. The editor's month, week and weekday option lists were seen in all ten display languages, in the order and length assumed; still open: reading calendar rows with them in a language other than Dutch on a real iTM. `events_between()` gives the events of a range of time, the period and special days included; it gives an event in a DST gap or overlap once (fold 0), which is a choice of the library: how the iTM runs such an event is still to see (a throwaway program with an event at 02:30 on the two DST days, and the history). |

## Left out on purpose

These can be added, but each needs a good reason and care. Read the reason before
starting.

| What | Why it is left out | What it would take |
| :--- | :----------------- | :----------------- |
| **Service writes**: time zone, dealer options, licence activation, changeover option, contact | Installer settings behind the service password. A wrong value can make the iTM unusable or need a reboot, and dealer options change what the iTM does. These service screens are read only; the service writes that are built (demand pulse and ports, R32 output ports, layout setup, the energy navigator's installer settings, disabling energy saving, the leakage check) each need `allow_service_change` or their own guard. | A clear use case, a guard flag per write, and tests on a device that may be reconfigured. |
| **Destructive service functions**: bus scan (A/C auto registration), DIII-NET management, history deletion | They re-register or remove equipment or data on the device. A bus scan can change which units the iTM knows. | Probably never as library calls; at most a documented, guarded expert function. |
| **Point data registration** (about 27 installer screens) | The installer's registration of management points: how the iTM addresses each unit. Wrong data breaks control of the units. | An installer use case and a test device. |
| **Starting an emergency stop** | The web UI has no way to start one; only the iTM's input can. Releasing and managing programs are built. | Nothing: this stays out. |
| **Network changes without a guard**: IP settings, web server ports, remote management | A wrong value locks every client out of the iTM until someone is at the panel. These writes exist, but only behind `allow_network_change` / `allow_remote_change`, and were validated live as a dry run. | Stays guarded. |
| **Touch panel calibration** | Needs someone touching the panel. | Not possible from the web UI. |
| **The graphical layout view** | It shows a floor plan only after an installer has set one up in the service screens (layout setup). | An iTM with a layout. |
| **Live writes of the dealer-option functions**: interlock, temperature limit, sliding temperature, heating mode optimisation, demand control | Built: readers validated on the empty screens, writes tested against the simulated iTM. They have not been validated with the options switched on; dealer options need no key (an installer switches them on in the service screens, then the iTM reboots), but whether the functions act while switched off is unknown. Demand control also needs a pulse input. | Switching the options on (a reboot) and testing on a throwaway group or program. |
| **Refusing plain HTTP for typed passwords** | Only the web login is hashed; the service, web user, own, touch panel and e-mail server passwords go in clear over http. Plain HTTP is the only transport the iTM is known to offer, so refusing it would break those calls; the client warns once instead (see the README's security notes). | An iTM known to serve HTTPS, and a TLS option for the client (a certificate fingerprint pin). |
| **Write counts across clients and restarts** | `writes_sent`, `recent_writes` and the write budgets count what one client sent, in memory. Other clients and accounts writing to the same units aren't counted, the counts start again with a new client, and both budgets are off by default, so nothing a caller does today is refused. Home Assistant keeps one client per iTM and can pass its own limits and store the counts it gets through `on_write`. | A use case with several clients of one iTM in one process (a count per iTM like the session lock), or persisted counts (a store like `SessionStore`). |
| **Paid licences**: PPD results, energy navigator data | These need an activation key (MAC address plus software ID), and none was available for development. | A contributor with a licensed iTM. |

## How you can help

The most useful contributions come from installations that differ from the one
the library was tested on (firmware Ver1.32.00): another iTM model or firmware
version, other equipment (ventilation units that report their mode and air
volume, hot water, reheat, output points), licences or dealer options, or another
display language.

1. **Open an issue first** with what your iTM has and what you'd like to add
   (see [CONTRIBUTING.md](CONTRIBUTING.md)).
2. **Capture what the web UI does.** The web UI talks to the iTM with
   `POST /cmd/` requests. Record them with the browser's developer tools (network
   tab, saved as HAR) while you use the function, or with `itm --trace FILE ...`,
   which writes each request's numbers (never its text, so not the login) and
   each reply with its session token blanked.
3. **Remove your installation's values before sharing anything**: names,
   descriptions, addresses, IP and MAC addresses, e-mail addresses, credentials,
   session tokens, readings, schedules and captured dates. Replace them with
   invented values (and correct each string's length prefix), so the replies
   still decode. Never share an export, backup or history archive as is: they
   contain the iTM's setup and authentication data.
4. **Build against the simulated iTM** (`tests/fake_itm.py` and the fakes next to
   it), so the function is tested without a device, and mark it in
   [FEATURES.md](FEATURES.md) as validated on a real iTM only once it was.

Writes on a real iTM change a live installation. Test them when nobody depends
on it, with a change you can undo, and read the result back in a new session,
as the library does for every write.
